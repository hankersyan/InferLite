# gRPC interface (Phase 5)

InferLite exposes a KServe / Triton Inference Server v2–compatible gRPC
interface (`inference.GRPCInferenceService`), in addition to its native HTTP
REST API. Both protocols share the same inference core
(`InferLite::runInference`), so validation, scheduling, audit logging and error
taxonomy are identical regardless of transport.

## Supported RPCs

All are synchronous unary RPCs (streaming is out of scope):

| RPC                | Purpose                                            |
|--------------------|----------------------------------------------------|
| `ServerLive`       | Process liveness                                   |
| `ServerReady`      | Readiness (models loaded + self-test passed)       |
| `ServerMetadata`   | Server name / version / extensions                 |
| `ModelReady`       | Per-model readiness                                |
| `ModelMetadata`    | Model name / versions / platform / I/O specs       |
| `ModelConfig`      | Model configuration (diagnostic dump)              |
| `ModelInfer`       | End-to-end inference (KServe `ModelInferRequest`)  |

The wire protocol is defined in `proto/grpc_service.proto`. C++ stubs are
generated by `protoc` + `grpc_cpp_plugin`; Python stubs (for tests) are
generated by `scripts/gen_grpc_py.ps1`.

## Build (opt-in)

gRPC is **disabled by default**; the default build is HTTP-only and is
unaffected. To enable against a vcpkg source-built gRPC:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\build_grpc.ps1                    # gRPC, CPU
powershell -ExecutionPolicy Bypass -File scripts\build_grpc.ps1 -Gpu               # gRPC + TensorRT GPU
powershell -ExecutionPolicy Bypass -File scripts\build_grpc.ps1 -GrpcRoot <sdk>    # custom gRPC SDK
```

When built with `-Gpu`, the TensorRT runtime DLLs (`nvinfer_10.dll`,
`nvinfer_plugin_10.dll`, `nvonnxparser_10.dll`, and the builder-resource DLLs)
are copied next to `inferlite.exe` so the server runs without TensorRT on
`PATH`; the CUDA runtime (`cudart64_*.dll`) comes from the system PATH. The
server reports `gpu.enabled: true` in `/v2/health/detailed`. Note that running
actual TensorRT engines requires a GPU with SM ≥ 7.5 (TensorRT 10.x
constraint); on older GPUs the build and GPU reporting work but TRT engine
build/inference is hardware-limited.

This configures with `-DINFERLITE_ENABLE_GRPC=ON -DGRPC_ROOT=<sdk>` and builds
into `build-grpc/inferlite.exe`. Equivalent manual configure:

```
cmake -S . -B build-grpc -DINFERLITE_ENABLE_GRPC=ON -DGRPC_ROOT=<dir>
```

`GRPC_ROOT` must contain `include/grpcpp/grpcpp.h`, `lib/grpc++.lib`, and the
`protoc` / `grpc_cpp_plugin` tools (under `bin/` or `tools/*`).

### Recommended: build gRPC with vcpkg

```powershell
# Build gRPC (and deps) with the same MSVC toolchain as InferLite.
vcpkg install grpc --triplet x64-windows
```

Then set `GRPC_ROOT` to the install prefix (e.g.
`C:\Test\vcpkg\vcpkg-2024.12.16\installed\x64-windows`). vcpkg exports proper
CMake targets, and InferLite links `gRPC::grpc++`, which carries the full
transitive dependency set (gRPC++/gRPC core, upb, address_sorting, re2, zlib,
c-ares, OpenSSL, and the Abseil components). vcpkg builds the gRPC core as a
**static** library even in the `x64-windows` (DLL) triplet, while Abseil /
protobuf / re2 / c-ares / zlib / OpenSSL are DLLs; the exported target handles
that mixed linkage correctly.

### Import libraries (prebuilt DLL-stack SDKs only)

If you point `GRPC_ROOT` at a prebuilt **DLL** gRPC stack (e.g. Anaconda),
`scripts/gen_grpc_importlibs.ps1` regenerates the stale DLL import libraries
directly from the shipped DLLs (the shipped `grpc++.lib` omits
`grpc::Status::OK`, and `libprotobuf.lib` omits protobuf internal globals).
CMake detects the DLL-stack layout (presence of `bin/grpc++.dll`) and does this
automatically.

## Run

```powershell
build-grpc\inferlite.exe --model-repository=... --http-port=8000 --grpc-port=8001
```

`--grpc-port` defaults to `0` (gRPC listener disabled); set it to enable gRPC.

## Test

```powershell
powershell -ExecutionPolicy Bypass -File scripts\test_grpc_server.ps1
```

The test probes the HTTP/2 listener, issues one `ServerLive`, and — if the
runtime is healthy — runs the full RPC suite and an HTTP regression check.

## Runtime / ABI requirement

The gRPC C++ runtime must be **built with an MSVC toolchain whose STL/CRT ABI
matches** the compiler used to build InferLite. A prebuilt gRPC stack from a
different MSVC version (e.g. the Anaconda DLLs, which import the older
`MSVCP140.dll` from a 14.2x-era toolchain) causes an **access violation
(0xC0000005) on RPC dispatch** — even a trivial `ServerLive` — because
protobuf/gRPC objects cross the STL-ABI boundary with a different layout. The
listener binds and speaks HTTP/2, but the first incoming RPC crashes the
process. HTTP-only serving is unaffected.

**Fix:** build gRPC from source with the same MSVC toolchain (vcpkg does this
for you), or obtain a prebuilt gRPC built with that exact toolchain. The
vcpkg-built SDK is confirmed to run the full gRPC suite with all PASSes.
